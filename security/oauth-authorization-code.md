# OAuth 2.0 でどのフローを使うか

OAuth 2.0 でアクセストークンを取るときに、どのフローをどう守って使うかを比べる。
中心は **認可コードフロー** で、それを **client_secret**、**PKCE**、**BFF（Backend for Frontend）** のどれで守るかを並べる。
あわせて、用途が違う Client Credentials と Device Authorization Grant、使うべきでない Implicit と Resource Owner Password Credentials の扱いも整理する。

本ファイルは特定のクラウドに依存しないので、`security/` に置く。

## 1. 解きたい課題と前提

「認可コードフローと PKCE のどちらを使うか」とよく言われるが、両者は二者択一ではない。
PKCE は認可コードフローに足す **拡張** であり、client_secret とは守るものが違う。

- **client_secret**: トークンエンドポイントで「このクライアントは本物か」を確かめる（クライアントの認証）。
- **PKCE**: 認可コードを「そのフローを始めたクライアントのセッション」に結びつける。盗まれたり差し込まれたりした認可コードを使えなくする。

そのため、実際の選択は「認可コードフローを、secret だけで守るか、PKCE だけで守るか、両方で守るか、トークンをブラウザに置かない BFF にするか」になる。

前提は次のとおりとする。

- 仕様は、執筆時点（2026 年 11 月）で次のものを基準にする。
  - RFC 6749（OAuth 2.0）、RFC 7636（PKCE）
  - RFC 9700（OAuth 2.0 Security Best Current Practice、2025 年 1 月）[^rfc9700]
  - RFC 10017（OAuth 2.0 for Browser-Based Applications、2026 年 8 月）[^rfc10017]
  - OAuth 2.1 は執筆時点でまだ Internet-Draft である。PKCE の必須化や Implicit の削除など、内容は RFC 9700 とほぼ揃っている[^oauth21]。
- クライアントの種類は次の 2 つに分ける。
  - **機密クライアント（confidential client）**: secret などの認証情報をサーバー側に安全に持てる。サーバーで動く Web アプリ、BFF など。
  - **公開クライアント（public client）**: 認証情報を安全に持てない。ブラウザだけで動く SPA、スマートフォンやデスクトップのネイティブアプリなど。配布物に secret を埋め込んでも、取り出せるので秘密にならない。
- PAR（RFC 9126）、DPoP（RFC 9449）、private_key_jwt などの強化策は、必要に応じて触れるにとどめる。

## 2. 構成

### 認可コードフローの流れ

```
利用者のブラウザ ─(1) 認可リクエスト──────────────▶ 認可サーバー
                 ◀─(2) リダイレクト（認可コード）──
クライアント ────(3) 認可コード + 認証情報 ─────────▶ トークンエンドポイント
             ◀───(4) アクセストークン（+ リフレッシュトークン）
```

認可コードは (2) でブラウザを経由するため、ここで漏れたり差し替えられたりしうる。
以下の構成の違いは、(3) で何を出して「正しい相手が、正しいセッションのコードを使っている」ことを示すかの違いである。

### A. 認可コード + client_secret（PKCE なし）

```
(1) 認可リクエスト: client_id, redirect_uri, state
(3) トークン交換:   code + client_secret
```

- 従来のサーバーサイドの Web アプリの形で、RFC 6749 の基本形である。
- 認可コードが漏れても、攻撃者は client_secret を持たないので、自分ではトークンに交換できない。
- ただし **認可コードの差し込み（code injection）** は防げない。攻撃者は盗んだ認可コードを、自分の端末で始めた正規クライアントとのフローに差し込む。正規のクライアントが自分の secret で交換してしまうので、攻撃者のセッションが被害者のリソースや ID に結びつく[^rfc9700]。
- CSRF は `state` で防ぐ。
- RFC 9700 は、機密クライアントでも PKCE を使うことを推奨（RECOMMENDED）している。OpenID Connect を使う機密クライアントは、トークンエンドポイントで得た ID Token の `nonce` を必ず検証し、検証に成功するまでどのトークンも使わないことを条件に、PKCE の代わりに `nonce` を使ってもよい（MAY）としている[^rfc9700]。

### B. 認可コード + PKCE（公開クライアント）

```
(1) 認可リクエスト: client_id, redirect_uri, code_challenge = SHA256(code_verifier), code_challenge_method = S256
(3) トークン交換:   code + code_verifier（secret なし）
```

- クライアントはフローのたびに使い捨ての乱数（code_verifier）を作り、そのハッシュだけを (1) で送る。(3) で元の値を出せるのは、フローを始めたクライアントだけである。
- secret を持てない SPA やネイティブアプリのための形で、RFC 9700 は公開クライアントに PKCE を必須（MUST）としている[^rfc9700]。
- 認可コードの横取りと差し込みの両方を防げる。認可サーバーが PKCE を確実に強制するなら、CSRF の対策も兼ねられる[^rfc10017]。
- ただし、クライアントが誰かは証明できない。同じ client_id を名乗る偽のアプリが、自分で PKCE を使ってフローを完走することは防げない（redirect_uri の厳密な一致で範囲を絞る）。
- SPA では、取ったトークンがブラウザの JavaScript から触れる場所に置かれる。XSS があれば盗まれうる。トークンをメモリにだけ置いても、XSS で新しい認可フローを裏で走らせて、新しいトークンを取られうる[^rfc10017]。
- リフレッシュトークンを公開クライアントに出す場合、送信者制約（DPoP など）かリフレッシュトークンのローテーションが必須（MUST）である[^rfc9700]。ブラウザのアプリに出す場合は、さらに最大の寿命か使われない期間での失効を設け、ローテーションのときに寿命を延ばさないことが求められる[^rfc10017]。

### C. 認可コード + client_secret + PKCE（機密クライアント）

```
(1) 認可リクエスト: client_id, redirect_uri, state, code_challenge
(3) トークン交換:   code + code_verifier + client_secret（または private_key_jwt など）
```

- A と B を重ねた形で、クライアントの認証と、認可コードとセッションの結びつけの両方を得る。
- 機密クライアントにとっての現在の標準形である。OAuth 2.1 のドラフトでは、OIDC の `nonce` を使う機密クライアントを除き、すべてのクライアントに PKCE を求めている[^oauth21]。
- 追加の手間は、code_verifier を作ってセッションに保存し、(3) で送る処理だけである。多くの OAuth / OIDC のライブラリは既定で対応している。
- client_secret の代わりに private_key_jwt（秘密鍵で署名した JWT でクライアントを認証する）を使うと、共有の secret を持たずに済み、ローテーションもしやすい。

### D. BFF（Backend for Frontend）

```
SPA ─(Cookie セッション)─▶ BFF（機密クライアント、C の構成）─(アクセストークン)─▶ API
                            └─ トークンはサーバー側にだけ置く
```

- SPA の背後に置いたサーバー（BFF）が機密クライアントとして C の構成で OAuth を行い、トークンはサーバー側にだけ保持する。ブラウザとは `HttpOnly`、`Secure`、`SameSite` を付けた Cookie のセッションでやり取りし、API の呼び出しは BFF が中継する。
- RFC 10017 はブラウザで動くアプリの構成を安全な順に BFF、Token-Mediating Backend、ブラウザ内の OAuth クライアント（B）の 3 つに整理し、業務用、機密性の高いアプリ、個人データを扱うアプリには BFF を強く推奨している[^rfc10017]。
- XSS があっても、トークンそのものはブラウザに出てこないので盗まれない。ただし、XSS の間は攻撃者が利用者のセッションで BFF に API を呼ばせることはできるので、XSS の対策が不要になるわけではない。
- Cookie を使うので、CSRF の対策（`SameSite`、カスタムヘッダーの要求など）が必要になる。
- サーバーを 1 つ持つことになり、API の呼び出しが BFF を経由する分の遅延と、セッションの保存先が加わる。

### E. Token-Mediating Backend

- バックエンドが機密クライアントとしてトークンを取り、アクセストークンだけをブラウザに渡す。API はブラウザから直接呼ぶ。
- BFF より中継の負荷が軽いが、アクセストークンはブラウザに出るので、XSS で盗まれうる。XSS でバックエンドに新しいアクセストークンを出させることもできる。リフレッシュトークンはバックエンドに残せる。
- RFC 10017 は、BFF のように API を中継できない事情があるときに検討する構成としている[^rfc10017]。

### 用途が違うフロー

| フロー                                           | 用途                                                                     | 補足                                                                                           |
| ------------------------------------------------ | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| Client Credentials                               | 利用者が介在しない、サーバー同士の呼び出し（バッチ、マイクロサービス間） | 機密クライアント専用。利用者の権限ではなく、クライアント自身の権限でトークンを取る             |
| Device Authorization Grant（RFC 8628）[^rfc8628] | テレビ、CLI など、ブラウザがないか入力が難しい端末                       | 端末に表示したコードを、利用者が別の端末のブラウザで入力して認可する。フィッシングに注意が要る |

### 使うべきでないフロー

| フロー                                      | 状況                                                                                                                                                                        |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Implicit（`response_type=token`）           | RFC 9700 は使わないこと（SHOULD NOT）としている。アクセストークンが URL に載って漏れやすい。OAuth 2.1 では削除される。SPA は B か D に移る                                  |
| Resource Owner Password Credentials（ROPC） | RFC 9700 は使ってはならない（MUST NOT）としている。クライアントが利用者のパスワードを直接受け取るため、多要素認証やフェデレーションとも相性が悪い。OAuth 2.1 では削除される |

## 3. トレードオフ

### 守れる攻撃の違い

| 攻撃                                               | A: secret のみ                                       | B: PKCE のみ                        | C: secret + PKCE                   | D: BFF                             |
| -------------------------------------------------- | ---------------------------------------------------- | ----------------------------------- | ---------------------------------- | ---------------------------------- |
| 漏れた認可コードを攻撃者が自分で交換する           | 防げる（secret がない）                              | 防げる（code_verifier がない）      | 防げる                             | 防げる                             |
| 盗んだ認可コードを攻撃者自身のセッションに差し込む | 防げない（OIDC の `nonce` を正しく検証すれば防げる） | 防げる                              | 防げる                             | 防げる                             |
| CSRF（攻撃者のフローを被害者に完了させる）         | `state` で防ぐ                                       | PKCE で防げる（AS が強制する場合）  | 防げる                             | 防げる                             |
| クライアントのなりすまし                           | 防げる                                               | 防げない（redirect_uri で絞るのみ） | 防げる                             | 防げる                             |
| XSS によるトークンの持ち出し                       | 該当しない（トークンはサーバー側）                   | SPA では起こりうる                  | 該当しない（トークンはサーバー側） | 該当しない（トークンはサーバー側） |
| client_secret の漏洩                               | 漏れると A の保護が消える                            | 該当しない（secret がない）         | PKCE の保護は残る                  | PKCE の保護は残る                  |

A、C、D でも、XSS の間に利用者のセッションで API を呼ばせることは防げない。
E は XSS の行を除いて D と同じである。XSS では、アクセストークンは盗まれうるが、リフレッシュトークンは守れる。

### 性能

- PKCE の追加の処理は、乱数の生成と SHA-256 のハッシュ 1 回で、無視できる。
- D（BFF）は API の呼び出しがすべて BFF を経由するため、1 ホップ分の遅延が加わる。BFF を API と同じリージョンに置けば小さく抑えられる。
- E と B は、ブラウザから API を直接呼ぶので、この遅延がない。

### コスト

- A、B、C の差は実装の数行で、費用の差はない。
- D と E は、BFF やバックエンドのサーバーと、セッションの保存先（Redis、DynamoDB、KV など）の費用が加わる。サーバーレス（Lambda、Cloud Run、Workers など）で組めば、少ないトラフィックでは小さい。
- 認証を外部の IdP（Auth0、Cognito、Entra ID など）に任せる場合、利用者がかかわるフロー（A〜E）の選択で料金は変わらないことが多い。料金は月間のアクティブユーザー数などで決まる。
- ただし Client Credentials のトークンは、M2M として別に課金したり上限を設けたりする IdP がある。料金ページで確認する。

### 運用負荷

- A と C は client_secret の保管とローテーションが要る。漏れると再発行してすべてのデプロイ先に配り直すことになる。private_key_jwt にすると公開鍵の登録で済み、ローテーションが楽になる。
- B は配る秘密がないので、秘密の管理は不要である。代わりに、リフレッシュトークンのローテーションか送信者制約を認可サーバー側で設定し、SPA ではトークンの保管場所と XSS 対策に気を配る。
- D はサーバーとセッションの運用、Cookie の属性と CSRF 対策、セッションの失効とトークンの更新の整合を持つ。
- 認可サーバー側では、PKCE を使えるようにするだけでなく、公開クライアントには必須にする[^rfc10017]。機密クライアントでも、code_challenge なしで発行したコードへの code_verifier 付きの交換を拒否する（PKCE のダウングレード対策）ことを確認する[^rfc9700]。PKCE を必須にすればこの対策も満たす。あわせて、`plain` ではなく `S256` だけを受け付ける設定を確認する。

### ロックイン

- どの構成も標準の仕様なので、IdP を替えても構成は保てる。
- ただし、IdP ごとに PKCE の強制、リフレッシュトークンのローテーション、private_key_jwt、DPoP への対応状況が違う。C や D の強化策に頼るほど、対応している IdP に選択肢が絞られる。
- D は自前の BFF を持つ構成なので、IdP の SDK に依存する度合いは逆に下がる。

## 4. 選ぶ基準

クライアントの種類ごとに、次の構成を基本にする。

| クライアント                               | 基本の構成                 | 補足                                                                                                                                       |
| ------------------------------------------ | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| サーバーサイドの Web アプリ                | C（secret + PKCE）         | A のままなら PKCE を足す。secret は private_key_jwt への移行を検討                                                                         |
| SPA（業務用、個人情報や決済を扱う）        | D（BFF）                   | RFC 10017 が強く推奨する形                                                                                                                 |
| SPA（低リスク、サーバーを持てない）        | B（PKCE、ブラウザ内）      | アクセストークンを短命にし、リフレッシュトークンはローテーションしたうえで最大の寿命を設ける                                               |
| ネイティブアプリ（モバイル、デスクトップ） | B（PKCE）                  | 外部ユーザーエージェント（システムのブラウザか、ASWebAuthenticationSession や Custom Tabs などのアプリ内ブラウザタブ）で認可する[^rfc8252] |
| サーバー同士の呼び出し                     | Client Credentials         | 利用者の権限が要るなら、認可コード系か Token Exchange を検討                                                                               |
| ブラウザのない端末、CLI                    | Device Authorization Grant | CLI でブラウザを開けるなら、ループバックへのリダイレクトと B でもよい[^rfc8252]                                                            |

迷ったときの原則は次の 3 つである。

- **PKCE は常に使う。** 機密クライアントでも害はなく、secret では防げない差し込みを防げる。
- **秘密を守れる場所があるなら、機密クライアントにする。** SPA でもサーバーを 1 つ置けるなら D にし、トークンをブラウザから遠ざける。
- **Implicit と ROPC は新しく使わない。** 既存のものは B、C、D のいずれかに移す。

[^rfc9700]: [RFC 9700: Best Current Practice for OAuth 2.0 Security](https://www.rfc-editor.org/rfc/rfc9700.html) を参照。PKCE は 2.1.1、Implicit は 2.1.2、リフレッシュトークンは 2.2.2 と 4.14.2、ROPC は 2.4、認可コードの差し込みは 4.5、PKCE のダウングレードは 4.8 節。

[^rfc10017]: [RFC 10017: OAuth 2.0 for Browser-Based Applications](https://www.rfc-editor.org/rfc/rfc10017.html)（BCP 212、2026 年 8 月）を参照。XSS の影響は 5.1 節、構成のパターンは 6 章（ブラウザ内クライアントの PKCE、CSRF、リフレッシュトークンは 6.3.2）、非推奨の構成は 7 章。

[^oauth21]: [The OAuth 2.1 Authorization Framework](https://datatracker.ietf.org/doc/draft-ietf-oauth-v2-1/)（Internet-Draft、draft-17、2026 年 10 月）を参照。PKCE は 7.5.1.1 節。RFC として公開されるまでに内容が変わることがある。

[^rfc8252]: [RFC 8252: OAuth 2.0 for Native Apps](https://www.rfc-editor.org/rfc/rfc8252.html) を参照。外部ユーザーエージェントは 4 章、ループバックへのリダイレクトは 7.3 節。

[^rfc8628]: [RFC 8628: OAuth 2.0 Device Authorization Grant](https://www.rfc-editor.org/rfc/rfc8628.html) を参照。フィッシングの注意は 5.4 節。
