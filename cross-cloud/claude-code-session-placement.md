# Claude Code のセッションをどこで動かすか

Claude Code のセッションを、手元の PC で動かすか、クラウドや自前のサーバで動かすかを比べる。
あわせて、途中で置き場所を移す方法と、スマホから進捗を追う方法を整理する。

本ファイルは、手元の PC、Anthropic のクラウド、AWS などの自前のサーバ、GitHub にまたがるため、`cross-cloud/` に置く。
内容は 2026 年 10 月時点の Claude Code の公式ドキュメントに基づく[^docs]。
Claude Code は更新が速いため、オプション名や挙動は変わりうる。

## 1. 解きたい課題と前提

Claude Code はふつう手元の PC のターミナルで動かすが、次のような場面で困る。

- 時間のかかる作業を任せたまま、PC を閉じて出かけたい。
- 外出先で、スマホから進捗を確かめたり、Claude の質問に答えたりしたい。
- 手元で動作確認をしない作業（ドキュメント、CI で確かめられる変更など）なら、最初から手元で動かす理由がない。

前提は次のとおりとする。

- claude.ai のアカウント（Pro、Max、Team、Enterprise）で Claude Code を使う。API キー、Amazon Bedrock、Google Cloud Vertex AI 経由の利用では、以下のクラウド系の機能の多くが使えない。
- リポジトリは GitHub にある。
- 対話しながら進める作業を主に扱う。定期実行のような自動化は、補足として 2 節の後半で触れる。

## 2. 構成

### A. 手元の PC だけで動かす

```
ターミナル ─▶ claude（手元の PC）
```

- ファイル、MCP サーバ、認証情報、社内 VPN など、手元の環境をすべてそのまま使える。
- PC を閉じるか、ターミナルを終了すると止まる。
- スマホからは見えない。

`claude --bg` で始めたセッションは、ターミナルを閉じても、PC がスリープしても動き続ける[^bg]。
`claude agents` で一覧を見て、`claude attach` で戻れる。
ただし、PC を起動しておく必要がある点は変わらない。

### B. 手元の PC で動かし、Remote Control で外から操作する

```
claude（手元の PC）◀─(アウトバウンドの HTTPS)─▶ Anthropic ◀─▶ claude.ai/code / Claude アプリ（スマホ）
```

- 動いているセッションで `/remote-control`（`/rc`）を実行するか、`claude --remote-control` で起動すると、claude.ai/code やスマホの Claude アプリから同じセッションを操作できる[^rc]。
- 実行するのはあくまで手元の PC である。会話の履歴、ファイル、MCP サーバはそのまま使え、移す作業が発生しない。
- PC を起動し、`claude` のプロセスを動かし続ける必要がある。スリープから戻れば自動でつなぎ直すが、シャットダウンすると止まる。
- `/config` で「Push when actions required」などを有効にすると、Claude が判断を求めたときや作業を終えたときに、スマホにプッシュ通知が届く。
- インバウンドのポートは開かない。接続している間、会話の記録は Anthropic のサーバに置かれる。
- Team と Enterprise では、組織のオーナーが管理画面で有効にする必要がある。LLM ゲートウェイを経由している（`ANTHROPIC_BASE_URL` を変えている）場合や、Zero Data Retention の構成では使えない。

### C. 自前のサーバで動かし、Remote Control で外から操作する

```
SSH ─▶ EC2 など（tmux の中で claude --remote-control）◀─▶ Anthropic ◀─▶ claude.ai/code / スマホ
```

- B の手元の PC を、常に起動している自前のサーバ（EC2、自宅のサーバなど）に置き換えた形である。
- 公式のドキュメントは、SSH 先で動かすときは `tmux` か `screen` の中で起動するよう勧めている[^rc]。常に起動しているマシンで動かし、ほかの端末から操作する使い方は、Remote Control の用途として公式に挙げられている[^self-hosted]。
- 手元の PC を閉じても止まらず、サーバに入れた MCP サーバや認証情報を使える。
- サーバの費用と、OS や認証情報の管理は自分で持つ。

### D. Anthropic のクラウドで動かす（クラウドセッション）

```
claude.ai/code / Claude アプリ / claude --cloud ─▶ Anthropic が管理する VM（GitHub から clone）
```

- Anthropic が管理する、セッションごとに隔離された VM で動く[^web]。始め方は次のとおりである。
  - ブラウザの claude.ai/code か、スマホの Claude アプリの Code タブから始める。
  - ターミナルで `claude --cloud "<依頼>"` を実行する。旧名の `--remote` も、非推奨の別名として使える。
  - デスクトップアプリで、環境に Cloud を選ぶ。
- リポジトリは GitHub から clone される。`claude --cloud` は今のブランチを使うため、**push していないコミットは含まれない**。
- PC を閉じても動き続ける。claude.ai/code とスマホの Code タブの一覧に出て、進捗を見ること、質問に答えること、指示を足すことができる。
- 変更はブランチに push され、claude.ai から PR を作れる。
- 環境（Cloud environments）ごとに、ネットワークの許可範囲、環境変数、セットアップスクリプトを決める。既定ではパッケージレジストリなどの許可リストにある通信しかできない。
- 手元の MCP サーバ、認証情報、社内ネットワークは使えない。
- しばらく操作しないと環境が回収される。再開すると会話は戻るが、動いていたコマンドやサブエージェントは戻らない。
- VM の料金は別にかからず、通常の利用上限から消費される。

Team と Enterprise では、同じ使い勝手のまま、組織のインフラ上でクラウドセッションを動かす **self-hosted environments**（ベータ）も使える[^self-hosted]。
組織のネットワークの中に runner を置き、runner が claude.ai からセッションを取りに行く。

### E. 手元のセッションから、クラウドのサブエージェントに作業を任せる

```
claude（手元の PC）─(Agent ツール、isolation: remote)─▶ クラウドで動くサブエージェント
        ▲                                                      │
        └──────────────────── 結果の報告 ─────────────────────┘
```

- 手元のセッションの Claude が、Agent ツールで `isolation: "remote"` を指定してサブエージェントを起動すると、サブエージェントがクラウドの環境で動く。プロンプトで「サーバで続きをやって」と頼むと、Claude がこの手段を選ぶことがある。
- この機能は、執筆時点で公式のドキュメントに記載がなく、使えるかどうかはアカウントによる。以下は実際に使って観察した挙動である。
- サブエージェントは、呼び出した手元のセッションの**子**として扱われる。
  - claude.ai/code やスマホの Code タブの一覧には**出ない**。
  - 結果は呼び出した手元のセッションに返る。手元のセッションが止まっている間は、報告を受け取れない。
- 作業そのものはクラウドで進み、PR などの成果は GitHub に残る。途中経過をスマホで追いたい場合は、issue へのコメントなど、GitHub に進捗を書かせる工夫が要る。

### 補足: 対話しない実行

対話しない自動化には、次の手段がある。
本ファイルでは深入りしない。

| 手段                                        | 動く場所                       | 起動のきっかけ                                     |
| ------------------------------------------- | ------------------------------ | -------------------------------------------------- |
| Scheduled tasks（`/schedule`、旧 Routines） | Anthropic のクラウド           | スケジュール、API、GitHub のイベント               |
| GitHub Actions（claude-code-action）        | GitHub のランナー              | Issue や PR のコメントの `@claude`、任意のイベント |
| `claude -p`、Agent SDK                      | 呼び出した側（サーバ、CI）     | 自前のスクリプト                                   |
| Slack（Claude Tag、旧 Claude in Slack）     | Anthropic のクラウド           | Slack のメンション                                 |
| Dispatch（デスクトップアプリ、Pro と Max）  | 手元の PC のデスクトップアプリ | スマホなどから依頼を送る                           |

Scheduled tasks の実行結果は、claude.ai/code の一覧から開いて、そのまま対話を続けられる[^routines]。

## 3. 置き場所を移す方法

置き場所を途中で移す手段は、向きによって大きく違う。

| 向き                                  | 手段                                                    | 会話の引き継ぎ                   |
| ------------------------------------- | ------------------------------------------------------- | -------------------------------- |
| 手元 → 外から操作                     | `/remote-control`（B）                                  | そのまま（移していない）         |
| 手元 → クラウド（CLI）                | push して、`claude --cloud "<依頼>"` で**新しく**始める | **引き継がれない**。依頼文に書く |
| 手元 → クラウド（デスクトップアプリ） | セッションの「Open in」から Cloud を選ぶ                | 要約して引き継ぐ                 |
| 手元 → クラウドのサブエージェント     | Agent ツールの `isolation: "remote"`（E）               | 依頼文に書いた内容だけ           |
| クラウド → 手元                       | `claude --teleport`、`/teleport`（`/tp`）               | そのまま取り込む                 |

公式のドキュメントは、CLI からの引き継ぎを一方向だと明記している[^web]。
手元で動いているターミナルのセッションを、そのままクラウドに送る手段はない。
`claude --cloud` に移るときは、会話の文脈が失われる。
そのため、次の作業を先に済ませておくとよい。

1. 作業中の変更を commit し、ブランチを push する。
2. 「どこまで終わったか」「次に何をするか」「決めたこと」を、リポジトリの中のファイル（計画のメモなど）に書いて push する。
3. `claude --cloud "<メモのファイル>を読んで続きをやって"` のように、メモを指して依頼する。

`/teleport` で取り込むには、手元の作業ツリーがクリーンであること、同じリポジトリであること、クラウド側のブランチが push 済みであることが要る。
取り込んだ後の作業は手元で進み、claude.ai 側には反映されない。
取り込んだ後もスマホで追うには、手元でもう一度 `/remote-control` を実行する。

## 4. トレードオフ

### 機能の差

| 観点                   | A: 手元   | B: 手元 + Remote Control | C: 自前サーバ + Remote Control | D: クラウドセッション          | E: クラウドのサブエージェント |
| ---------------------- | --------- | ------------------------ | ------------------------------ | ------------------------------ | ----------------------------- |
| 動く場所               | 手元の PC | 手元の PC                | 自前のサーバ                   | Anthropic の VM                | クラウド                      |
| PC を閉じても動くか    | 動かない  | 動かない                 | 動く                           | 動く                           | 動く（報告は受け取れない）    |
| スマホで見る・操作する | できない  | できる                   | できる                         | できる                         | できない                      |
| スマホへのプッシュ通知 | なし      | あり                     | あり                           | あり                           | なし                          |
| 手元の MCP・認証情報   | 使える    | 使える                   | サーバに入れたものを使える     | 使えない                       | 使えない                      |
| 社内ネットワーク       | 使える    | 使える                   | サーバしだい                   | 使えない（self-hosted なら可） | 使えない                      |
| push していない変更    | 使える    | 使える                   | サーバ上にあれば使える         | 使えない                       | 使えない                      |
| 会話の文脈             | —         | そのまま                 | そのまま                       | 新しく始まる                   | 依頼文だけ                    |

### コスト

- A、B、D、E は、いずれも Claude のプランの利用上限から消費される。クラウドセッションに VM の別料金はかからない。
- C は、これに加えて自前のサーバの料金がかかる。EC2 なら t4g.small で月 12 USD 程度から（us-east-1）。
- 対話しない手段のうち、GitHub Actions はランナーの実行時間の料金がかかる。

### 運用負荷

1. D: 環境は Anthropic が用意する。環境のネットワーク設定とセットアップスクリプトを決めるだけでよい。
2. A、B: 追加の運用はない。B は PC を閉じないように気をつける必要がある。
3. E: 運用はないが、途中経過を追う仕組みを依頼文に組み込む必要がある。
4. C: サーバ、OS、Claude Code の更新、認証情報の管理を自分で持つ。

### セキュリティ

- B と C は、外から手元の PC やサーバを操作できる経路になる。Claude のアカウントが乗っ取られると、手元の環境で任意の操作をされうる。
- D の VM には Git の認証情報が入らず、Anthropic のプロキシ経由で付与される。手元の秘密情報が VM に渡ることもない。
- D で外部と通信させるほど、ネットワークの許可範囲を広げることになる。必要なドメインだけを許可する。

## 5. 選ぶ基準

A（手元だけ）が向くのは次のような場合である。

- 手元で動作確認しながら進める。
- 席を離れる予定がない。

B（手元 + Remote Control）が向くのは次のような場合である。

- 手元で始めた作業を、少しの間だけ席を離れて、スマホで見守りたい。
- 手元の MCP サーバや社内ネットワークに依存していて、クラウドに移せない。
- PC を開いたままにできる。

C（自前サーバ + Remote Control）が向くのは次のような場合である。

- 手元と同じような環境（MCP サーバ、社内ネットワーク）が必要で、かつ PC を閉じても動かしたい。
- サーバを管理できる。

D（クラウドセッション）が向くのは次のような場合である。

- 手元で動作確認をしない作業。ドキュメント、CI で確かめられる変更、調査など。
- PC を閉じて、スマホで進捗を追いたい。
- 最初から D で始めれば、文脈を引き継ぐ手間そのものが発生しない。

E（クラウドのサブエージェント）は、手元のセッションで計画を立て、決まった作業だけをまとめて任せたい場合に使える。
ただし、スマホからは見えず、結果は手元のセッションに返る。
スマホで追いたいなら、D を使うよう明示して頼むほうが確実である。

### 推奨する使い分け

「基本は手元で、ときどきサーバに任せ、スマホで進捗を追う」場合は、次のように使い分ける。

1. 手元で動作確認をしない作業は、最初から D で始める。
2. 手元で始めた作業を少しの間だけ見守るなら、B（`/rc`）にする。
3. PC を閉じるなら、引き継ぎのメモを push してから、`claude --cloud` で D に移る。Claude に頼むときは「`claude --cloud` で続きをやって」と手段まで指定する。「サーバで続きをやって」とだけ頼むと、E が選ばれてスマホから見えないことがある。
4. クラウドの結果を手元で確かめるときは、`/teleport` で取り込む。
